## STREAM構成

### S: 良いオフショアベンダーは、日本価格の半額で爆速の成果を出す（〜250字）
→ 結論を冒頭で太字明示：「オフショア開発はリスクがあるが、良いベンダーを見つければ日本価格の半額で比較的質の高い成果物を爆速で出してくれる。大企業相手に継続受注している事例は実在する」
→ 読者の困りごと：「3ヶ月経っても何も出来上がらない」「報告は順調なのに実物がない」「クレームを言っても改善されない」
→ 5案件（インド・ベトナム）の経験から、訴訟寸前の失敗と継続受注の成功の両方を経験した事実を提示

### T: 「属性が違うと、同じ言葉が違う意味になる」という構造（〜350字）
→ レンズ：「属性差によるコミュニケーションギャップ構造」
→ 国・職種・企業文化が異なると、交わす言葉の気になるポイントが根本的に違う
→ 代表例：インド人の「できます」は「できるように努力することができます」
→ チーム内（同属性）でコミュニケーションに苦労した経験がないため、異属性間のギャップを過小評価してしまう
→ このレンズで見ると：オフショアの失敗は「スキル不足」ではなく「思考フローの構造的なズレ」の問題

### R: 「順調です」が3ヶ月続いたら、何もできていない（〜600字）
→ Tのレンズで3つの構造を分解：
  - 構造①「報告と実態の乖離」：「環境構築中だが実装は進んでいる」が3ヶ月続いた実体験。デモを求めても出てこない＝できていない
  - 構造②「祈りの罠」：この局面を乗り越えれば好転するかもという祈りレベルの望み。上司も同じ心理で組織ぐるみで身動きが取れなくなる
  - 構造③「炎上中の心理的負荷」：火消しだけで精一杯。別ベンダーとの契約調整やクライアントへの説明を考える余裕がない
→ 実体験：思いっきりクレームを言って訴訟寸前になったのに、後日「また機会があったらぜひ仕事ください」と言ってくるベンダーが存在した事実

### E: 祈り続けた3ヶ月のコスト（〜300字）
→ 放置コストの可視化：3ヶ月以上のスケジュール遅延、立て直しに半年、訴訟リスク、クライアント信頼喪失
→ コミカルな例え話：「『明日届きます』と毎日言い続ける国際宅配便に3ヶ月付き合い、届いた箱を開けたら注文と全く違うものが入っていた」
→ 最大の損失は時間：炎上中は冷静な判断ができず、構造的な対策が遅れ、損失が雪だるま式に拡大する

### A: 契約前・開発中・危機時の3段階で構造を変える（〜750字）
→ 改善策を「タイミング別」に整理（なぜ効くかの構造的説明とセット）：

  1. **契約前：ベンダー選定の4つの急所**
     - 日本法人の有無 → 法的リスクの構造的低減（事前のリスクコントロールに限る）
     - ISO/CMMI認証・実績 → 品質管理が仕組み化されている証拠
     - 会社の成長速度 → 優秀なエンジニアが集まっているかの指標
     - ブリッジSEの質 → 通訳ではなく、プロダクトを理解し意見が言えるレベルか面談で確認

  2. **開発中：デモベースの進捗確認**
     - 開発初期から環境を操作させてもらい、動くもので確認
     - 「できている」のにデモができない＝できていないと判断
     - デモで注文と違うものが出てきたら、構造的対策（ベンダー変更・体制変更）が必須

  3. **危機時：祈るな、構造を変えろ**
     - ベンダー切替 ＋ 社内体制構築の2並列体制
     - 一本足打法のリスクを回避し、確実に前進できる体制を確保
     - 課題解決速度を見える化して監視、クライアントにも共有 → [PM系ツールリンク]

→ 最初の一歩：「日本法人があるオフショアベンダーを探し、ブリッジSEと面談する」

### M: リスクを捉えた瞬間に動ける体制を持つ（〜300字）
→ コミュニケーションの原則：オブラートに包まず率直に、ただし敬意は必ず持つ
→ 定着の仕組み：
  - ベンダー選定チェックリスト（4つの急所）をテンプレート化して組織で共有
  - 開発初期からのデモスケジュールを契約時に合意
  - 月次で「報告と実態の乖離」がないか、動くもので確認する習慣
→ 締め：「リスクを捉えたら最速で最大限の対策を打つ。長期的に正しいと思ったことに自信を持って舵を切る。それがオフショア開発を"使いこなす"ための構造」
