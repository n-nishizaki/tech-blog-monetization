## STREAM型とは

STREAM型は、「システム思考実践ノート」ブログ専用に設計された記事構成フレームワークです。

従来のPREP型やSPIRAL型と異なり、**読者に「思考のレンズ」を先に渡す**ことで、構造理解を促進し、腹落ち感を高めることを目的としています。

---

## STREAM型の構造

```
S: Summary & Situation（結論＋日常現象）
T: Thinking Lens（思考のレンズ）
R: Root Structure（根本構造）
E: Effect（放置するとどうなるか）
A: Adjustment（介入・改善策）
M: Mechanism（定着の仕組み）
```

---

## 各セクションの詳細

### S: Summary & Situation（結論＋日常現象）

**目的**: 読者の「読む意味」を即座に提示する

**内容**:
1. この記事で得られる結論（1-2文）
2. 読者が日常で遭遇する具体的な困りごと・現象

**文字数**: 200-300字

**書き方のポイント**:
- 結論を先に明示（「〇〇すれば、△△できる」）
- 日常現象は具体的に（「あなたも経験ありませんか？」形式）
- 読者の「自分ごと」として認識させる

**例（オフショア開発）**:
```
オフショアベンダーを選ぶ際、日本法人があるかどうかを最優先で確認すべきです。

「3ヶ月経っても何も出来上がってこない」
「報告は順調と言っているのに、実際には全く進んでいない」
「クレームを言っても改善されず、訴訟寸前まで発展」

もしあなたがオフショア開発でこんな経験をしたことがあるなら、
ベンダー選定の段階で構造的なリスクを見落としていた可能性があります。
```

---

### T: Thinking Lens（思考のレンズ）

**目的**: 問題を理解するためのシステム思考の概念を導入し、読者に「見え方」を先に渡す

**内容**:
1. この問題を理解するために必要なシステム思考の概念
2. なぜこのレンズが有効なのか
3. このレンズで見ると何が見えるのか

**文字数**: 300-400字

**書き方のポイント**:
- システム思考の専門用語は避け、平易な言葉で
- 「このレンズで見ると〇〇が見える」という形で具体化
- 図解を積極的に活用（コードブロック内のASCIIアートでよい）
- **レンズは普遍的な原則を優先する**: 特定の状況（オフショア、転職等）に限定したレンズより、「構造的な問題には構造的な対策でしか対処できない」のような普遍的な原則の方が、読者の応用範囲が広がり記事の価値が高まる。状況固有の要素は「このレンズが特に機能しやすい状況」として補足する形にとどめる。

**例（オフショア開発）**:
```
オフショア開発の失敗は、「距離によるリスク増幅構造」として理解できます。

物理的距離が離れると、以下の3つのリスクが指数関数的に増大します：
1. コミュニケーションリスク（言語・文化・時差）
2. 契約リスク（法的管轄・紛争解決）
3. 品質リスク（仕様理解・レビュー頻度）

このレンズで見ると、ベンダー選定とは、
「これらのリスクをどれだけ構造的に低減できるか」という問題になります。

【図解：距離とリスクの関係図】
```

---

### R: Root Structure（根本構造）

**目的**: Tで得たレンズを使って、問題の本質的な構造を分解・整理する

**内容**:
1. 表層的な問題の裏にある構造
2. なぜその構造が問題を引き起こすのか
3. 構造の各要素間の関係性

**文字数**: 500-700字

**書き方のポイント**:
- Tで導入したレンズを明示的に使う
- 「〇〇だから△△になる」という因果関係を明確に
- 図解・構造図で可視化
- オーナーの実体験を織り込む

**例（オフショア開発）**:
```
「距離によるリスク増幅構造」を使って、オフショア開発の失敗パターンを分解してみましょう。

【第1層：コミュニケーションリスク】
- 言語の壁：英語での仕様伝達→微妙なニュアンスが伝わらない
- 文化の壁：「できます」の定義が異なる（日本：確実にできる / 海外：努力します）
- 時差の壁：リアルタイム調整が困難→問題発覚が遅れる

【第2層：契約リスク】
- 法的管轄の違い：紛争時、どの国の法律が適用されるか不明確
- 訴訟コスト：海外での法的手続きは時間・費用が膨大

【第3層：品質リスク】
- レビュー頻度の低下：距離があるため、細かい確認が後回しに
- 仕様理解の齟齬：「できている」と「要求を満たしている」の乖離

実際、私が担当したプロジェクトでは、
3ヶ月間「環境構築中、実装は順調」と報告されていたものの、
実際には環境構築すらできておらず、実装も全く進んでいませんでした。

この構造的な問題が、訴訟寸前まで発展した根本原因です。
```

### E: Effect（放置するとどうなるか）

**目的**: 構造が理解できた今、放置コストを可視化し、行動動機を生む

**内容**:
1. この構造を放置した場合の具体的な損失
2. 時間軸での悪化プロセス
3. コミカルな例え話で印象づける

**文字数**: 300-400字

**書き方のポイント**:
- 構造理解済みの読者に語りかける形
- 定量的な損失（時間・お金）を明示
- コミカルな例え話で記憶に残す
- ただし、過度に煽らない

**例（オフショア開発）**:
```
この構造を理解せずにベンダーを選ぶと、どうなるでしょうか。

まず、3ヶ月間「順調です」という報告を信じ続けます。
次に、納期直前になって「実は何もできていない」と発覚。
慌てて別のベンダーを探すも、すでに予算と時間を消費済み。
最悪の場合、訴訟に発展し、弁護士費用だけで数百万円。

これは、
「安いからという理由だけで海外のレストランに食材を発注したら、
 3ヶ月後に腐った食材が届き、返金も交換もできない」
という状況に似ています。

私のプロジェクトでは、
年間5,000万円の受託案件が、3ヶ月間完全停止。
訴訟寸前まで発展し、立て直しに半年を要しました。
```

### A: Adjustment（介入・改善策）

**目的**: シンプルで真芯を捉える改善策を提示し、読者に「やってみよう」と思わせる

**内容**:
1. すぐに実践できる具体的な改善策（3-5個）
2. なぜその改善策が構造的に有効なのか
3. 実践時の注意点

**文字数**: 600-800字

**書き方のポイント**:
- 「これだけやれば8割解決」という核心を突く
- 各改善策に対して「なぜ効くのか」を構造的に説明
- オーナーの実体験での成功例を盛り込む
- チェックリスト形式で実践しやすく

**例（オフショア開発）**:
```
では、どうすればこの構造的リスクを低減できるのか。
以下の3つのステップで、8割のリスクを回避できます。

【ステップ1：日本法人の有無を確認】
なぜ効く：法的管轄が明確になり、紛争時のコストが激減
実践方法：
- 日本に法人登記があるか確認
- 日本人のブリッジSEが常駐しているか確認
- 契約書の準拠法が日本法になっているか確認

【ステップ2：ISO/CMMI認証の確認】
なぜ効く：品質管理プロセスが標準化されている証拠
実践方法：
- ISO 9001（品質管理）の認証を確認
- CMMI レベル3以上を推奨
- 認証の有効期限も確認

【ステップ3：ブリッジSEとの相性確認】
なぜ効く：コミュニケーションリスクの大部分を担う人物の能力が鍵
実践方法：
- 契約前に必ずブリッジSEと面談
- 日本語での仕様理解力を確認
- 「できます」の定義をすり合わせ

実際、私が立て直しで採用したベンダーは、
この3つをすべて満たしており、以降のプロジェクトは順調に進みました。
```

---

### M: Mechanism（定着の仕組み）

**目的**: 改善策を一時的なものにせず、日常のフローに組み込む仕組みを示す

**内容**:
1. 改善策を習慣化・仕組み化する方法
2. フィードバックループの設計
3. 長期的に維持するためのチェック機構

**文字数**: 300-400字

**書き方のポイント**:
- 「やりっぱなし」にしない仕組み
- 定期的なチェックポイントを設計
- テンプレート・チェックリストなどのツールを提供
- システム思考の「ループ」概念を活用

**例（オフショア開発）**:
```
ベンダー選定は一度で終わりではありません。
以下の仕組みで、継続的にリスクを管理しましょう。

【仕組み1：ベンダー選定チェックリストのテンプレ化】
- 上記3ステップをチェックリスト化
- 新規ベンダー検討時に必ず使用
- 過去の失敗事例も追記していく

【仕組み2：月次レビューでリスク可視化】
- 毎月、3つのリスク（コミュニケーション・契約・品質）を定量評価
- スコアが低下したら即座に対策会議

【仕組み3：ブリッジSE評価の定期化】
- 四半期ごとにブリッジSEとの1on1
- 改善要望を伝え、相互理解を深める

この仕組みを回すことで、
「気づいたら手遅れ」という状況を構造的に防げます。
```

## STREAM型 vs SPIRAL型 比較表

| 要素 | STREAM型 | SPIRAL型 | 差分の意図 |
|------|----------|----------|------------|
| 結論提示 | S (Summary & Situation) | S (Summary & Situation) | 同じ |
| **概念導入** | **T (Thinking Lens) - 2番目** | R (Rule/Concept) - 4番目 | **レンズを先に渡す** |
| 本質分析 | R (Root Structure) - 3番目 | P (Problem Essence) - 2番目 | レンズで見た本質 |
| **損失可視化** | **E (Effect) - 4番目** | I (Impact) - 3番目 | **構造理解後に損失** |
| 改善策 | A (Adjustment) | A (Adjustment) | 同じ |
| 定着設計 | M (Mechanism) | L (Loop) | 名称変更のみ |

## STREAM型が優れている理由

### 1. オーナーの思考プロセスと一致
オーナーの思考OS：
1. 全体構造の把握（情報収集）
2. 本質の抽出（シンプル化）
3. 目的関数の定義
4. 安定化設計
5. 実装と検証

STREAM型は、この順序をそのまま反映しています。

### 2. 「思考のレンズ」を先に渡す効果
- 読者が構造を見る目を先に得る
- 本質説明時の理解度が向上
- 「ああ、そういうことか」という腹落ち感

### 3. 構造理解→損失認識の順序
- 感情的反応ではなく、構造的納得に基づく行動動機
- 損失の「意味」が理解できている状態で提示

### 4. システム思考ブログとの親和性
- 「システム思考実践ノート」というタイトルとの一貫性
- 各記事が「思考のレンズ」を提供する構造

## 執筆時の注意点

### 1. Tセクションでレンズを明確に提示
- 専門用語は避け、平易な言葉で
- 図解を必ず入れる
- 「このレンズで見ると〇〇が見える」と明示

### 2. RセクションでTのレンズを使う
- 「〇〇というレンズで見ると...」と明示的に参照
- レンズなしでは見えない構造を示す

### 3. Eセクションで感情に訴える
- 構造理解済みの読者に語りかける
- コミカルな例え話で印象づける
- ただし、過度に煽らない

### 4. 全体の一貫性を保つ
- S→T→R→E→A→Mの流れが自然につながる
- 各セクションで同じ「構造」を異なる角度から見る
