# blog-draft: STREAM型本文執筆

構成案ファイル: $ARGUMENTS

## このスキルの目的

承認済みの構成案（`blog-structure` の出力）とインタビュー記録を読み込み、
本文のみに集中して執筆する。構成設計は行わない。

---

## 事前確認

以下をすべて読み込む:

1. **構成案ファイル**: $ARGUMENTS（承認済みの構成案）
2. **インタビュー記録**: `コンテンツ制作/interviews/` 内の対応ファイル
3. **STREAM型定義**: `コンテンツ制作/docs/STREAM_FRAMEWORK.md`
4. **ブログコンセプト**: `コンテンツ制作/docs/BLOG_CONCEPT.md`
5. **既存記事（文体参考）**: `コンテンツ制作/drafts/article-01-long-term-investment-v5.md`

## 執筆の基本姿勢

このスキルの本質は**「インタビュー素材を読者価値に変換する翻訳作業」**である。
以下の5つの力を意識して執筆する。

### 1. 素材解釈 — 行間を読む
- インタビュー回答の文字面だけでなく、話者が**本当に伝えたかったこと**を汲み取る
- 複数の回答を横断して、一貫したストーリーラインを見出す
- 回答に含まれる具体的な数値・エピソードの中から、読者にとって価値ある情報を選別する

### 2. 話し言葉→読み言葉の変換
- インタビューの話し言葉（散らかりやすい）を、読み言葉（論理的な流れ）に変換する
- 抽象的な発言は具体例で補強し、具体的すぎる話は適切に一般化する
- 読者が「自分ごと化」できる粒度に調整する

### 3. 引用・要約・パラフレーズの使い分け
- **直接引用**（「」で囲む）: 感情が乗った印象的な言葉、具体的な数値を含む発言
- **要約**: 長い説明を短くまとめるとき。話者の意図を保ちつつ圧縮する
- **パラフレーズ**: 読者に馴染みやすい表現に言い換えるとき。元の意味を歪めない
- 一つの記事で直接引用は**3〜5箇所**を目安とし、多用しすぎない

### 4. 倫理的な編集判断
- インタビュイーの発言の趣旨を歪めない。都合の良い切り取りをしない
- 事実と意見の区別を明確にする（「〜という事実がある」vs「〜と感じた」）
- 公開前にオーナーが確認できるよう、元のインタビュー回答との対応を意識して書く

### 5. 構成への忠実さと柔軟さ
- 承認済み構成に忠実に書くことが基本
- ただし執筆中に「この順番では伝わりにくい」「素材が足りない」と気づいた場合は、完了レポートの確認事項に明記してオーナーに提案する（勝手に構成を変えない）

## 執筆手順

### Step 1: Jekyll front matter の作成

構成案の「基本設計」セクションをもとに作成:

```yaml
---
layout: post
title: "[承認されたタイトル]"
date: [作成日]
categories: [カテゴリー]
tags: [タグ1, タグ2, タグ3]
description: "[120-160字のメタディスクリプション（メインKWを先頭に含める）]"
status: draft
---
```

### Step 2: 本文執筆

構成案の各セクションを順番に執筆する。

**必須ルール（すべてのセクション共通）**:
- 見出しにSTREAM文字（S:, T:, R:, E:, A:, M:）を使わない → 自然な日本語見出し
- 「〜かもしれません」「〜と思います」を使わない
- 過度な煽り表現・根拠のない断定をしない
- インタビュー記録の実体験・数値を積極的に引用する
- 文体は既存記事（article-01）に合わせる
- インタビュイーの「生の言葉」（直接引用）とライターの「地の文」（解説・接続）を明確に切り替える
- 各セクションの冒頭にそのセクションの結論を置く（結論先行）

**セクション別の執筆ポイント**:

#### S（冒頭）
- 結論を**冒頭1〜2文で**明示する（太字推奨）
- 読者の困りごとを「あなたも、こんな経験ありませんか？」形式で描写
- インタビューQ1・Q2の回答を反映

#### T（思考のレンズ）
- レンズとなる概念を平易な言葉で説明
- 「このレンズで見ると〇〇が見える」と明示
- 図解をMarkdown形式で挿入（`【図解: ○○】` というプレースホルダーでもよい）

#### R（根本構造）
- 「〇〇というレンズで見ると...」とTを明示的に参照してから展開
- 構造を箇条書きや階層で整理
- インタビューの実体験エピソードを織り込む（具体的な数値付き）

#### E（放置コスト）
- 「この構造を理解した上で、放置するとどうなるか」という語り口
- 時間軸での悪化プロセスを描写
- コミカルな例え話で記憶に残す（ただし過度に煽らない）

#### A（改善策）
- 見出し: 「〇〇するための3つのステップ」など実践的なタイトル
- 各改善策に「なぜ効くか（構造的な説明）」と「実践方法」をセットで
- チェックリスト形式を活用して読みやすく
- アフィリエイトリンクのプレースホルダーを挿入:
  `[楽天カードの公式ページはこちら]`（実際のリンクはオーナーが設定）

#### M（定着の仕組み）
- 「やりっぱなし」にしない仕組みを2〜3個提示
- テンプレート・チェックリスト・定期チェックの設計を含める
- インタビューQ13の「実際にやっている仕組み」を引用

#### まとめ
- STREAM型の流れを100〜150字で振り返る
- 読者への「最初の一歩」（Q15の回答）で締める

---

### Step 3: ファイル保存

**命名規則**: `article-[XX]-[テーマの英語スラッグ]-v1.md`
**保存先**: `コンテンツ制作/drafts/`

### Step 4: 完了レポート出力

```
## ドラフト v1 作成完了

**ファイル**: コンテンツ制作/drafts/[ファイル名]
**文字数**: [本文文字数]字 / 目安 [目安文字数]字（[±XX%]）
**図解プレースホルダー数**: [XX]箇所
**アフィリエイト挿入箇所**: [XX]箇所

## オーナーへの確認お願い事項
1. 実体験エピソードの表現に不自然な点はありませんか？（元の発言の趣旨と乖離していないか）
2. 数値・固有名詞に誤りはありませんか？
3. 直接引用箇所の表現はご本人の意図と合っていますか？
4. 追加・修正したい点をフィードバックください。

## 構成に関する提案（該当がある場合のみ）
- 執筆中に気づいた構成上の改善提案があればここに記載する
- （例: 「Rセクションの素材が薄いため、追加インタビューを推奨」等）

## 次のステップ
- フィードバックを受けてv2を作成
- 最終版に対して `/blog-review [ファイルパス]` で60%基準チェック
```
