## この部門の責任

**売れる商品を市場に置くこと。**

「オーナーの強みを商品化する」ではない。「買い手が金を払う理由がある商品を作る」が正しい起点。オーナーの強みは商品の品質を担保する手段であって、商品設計の出発点ではない。

---

## 商品設計の原則

### 1. 買い手の検索行動から始める

```
× オーナーの強み → 商品化 → 出品
○ 買い手が何を探しているか → その言葉で商品を作る → オーナーの強みで品質を担保
```

買い手はココナラの検索窓に「壁打ち」とは打たない。「AI ツール 作成」「業務効率化 相談」「オフショア開発 相談」と打つ。商品名・タイトル・説明文は買い手の語彙で書く。

### 2. 出品ページの設計構造

出品ページの各要素には明確な役割がある：

```
タイトル ── 検索に引っかかる＋「これだ」と思わせる（具体的な成果物）
  ↓
プロセス説明 ── 「この人なら大丈夫だ」と安心させる（設計の進め方）
  ↓
成果物 ── 「これが手に入る」と購入を確定させる（納品物の明示）
  ↓
経歴・実績 ── 「この人は本物だ」と裏付ける（信頼の証拠）
```

**プロセスを見せる理由**: 買い手は「プロセス＋成果物」のセットで期待値を判断する。しっかりしたプロセスを見ると「自分の固有の状況でもちゃんとしたものが出てきそうだ」と思える。テンプレ対応ではないことが伝わる。

### 3. 具体的な成果物を入り口にする

```
× 「思考を整理します」 → 抽象的。何が手に入るかわからない
○ 「AI APIで専用ツールを作ります」 → 具体的。成果物がイメージできる
```

「テキスト壁打ち」「判断支援」は内部用語。買い手に見せる言葉ではない。買い手が想像できる具体的な成果物をタイトルに置く。

### 4. 商品の軽さを維持する

- **単発**: 買い手もオーナーも拘束されない
- **テキスト非同期**: オーナーの構造化力が最も活きる形式
- **スコープ明確**: やること・やらないことが明示されている
- **断れる構造**: 対応不可の場合に丁寧に断れる設計

## 市場調査のプロセス

商品を設計する前に、必ず以下を確認する。

### やること

1. **ココナラで実際に検索する**
   - 買い手が使いそうなキーワードで検索
   - 上位表示されている商品のタイトル・価格・評価を記録
   - 売れている商品（評価数が多い）のページ構成を分析

2. **競合の見せ方を分析する**
   - タイトルで何を約束しているか
   - プロセスをどう見せているか
   - 価格帯はどこか
   - 差別化ポイントは何か

3. **買い手の言葉を集める**
   - ココナラの相談カテゴリで使われている言葉
   - 買い手のレビューに出てくる言葉（「〇〇してもらえた」）
   - 検索サジェストに出てくるキーワード

### 調査結果の使い方

- 商品タイトルは買い手の検索キーワードから作る
- 説明文は買い手のレビューに出てくる言葉を使う
- 価格は競合の価格帯を見て設定する
- 差別化は競合がやっていないことから作る

## 商品コンセプト

### オーナーが提供できる価値
```
「混沌を構造化して、次の一歩を示す」
  ├→ パターン認識と構造化（自然にできる）
  ├→ 相手の中にある答えを引き出す（寄り添い型）
  └→ 技術とビジネスの両面を理解（12年の実務経験）
```

**注意**: これは商品の品質を担保する「中身」であり、そのまま商品名にはしない。

### 商品化の方向性

オーナーの強みを活かせる商品は複数ありうる。抽象的な1商品（壁打ち）ではなく、具体的なターゲット別に商品を設計する。

```
例:
- 「オフショア開発のベンダー選定、判断材料を整理します」
- 「AI導入の進め方、あなたの状況に合わせて整理します」
- 「炎上プロジェクトの立て直し方針を構造化します」
```

同じ「構造化して次の一歩を示す」でも、入り口が具体的なら買い手は「これは自分のことだ」と思える。

### 設計の型

どの商品でも共通する進め方：

1. **ヒアリング**: 状況と目的を聞く
2. **構造設計**: 問題の構造を可視化する
3. **論点整理**: 今決めるべきことを明確にする
4. **次の一歩**: 具体的なアクションを提示する

この進め方自体を出品ページに書く。買い手がプロセスを見て「ちゃんとやってくれそうだ」と感じることが信頼につながる。

## ブログとの連携

### 記事→商品の導線
```
記事を読む → 「この人の思考、自分の仕事にも使えそう」 → サービスページ → ココナラ
```

### 記事が商品を裏付ける仕組み
- 記事で「実際にこう構造化して解決した」を見せる
- 出品ページから記事にリンクし「こういう思考の型を使います」と示す
- 記事＝プロセスの実演。「この人は本当にできる」と伝わる証拠

## フィードバックと改善

### 見る指標

| 指標 | 何がわかるか | 対応 |
|------|-------------|------|
| 閲覧数 | タイトルが検索に引っかかっているか | 低い→タイトル・キーワードを変える |
| お気に入り数 | 興味は持たれているか | 閲覧多・お気に入り少→説明文を改善 |
| 購入数 | 買う決断に至っているか | お気に入り多・購入少→価格or信頼を改善 |
| リピート | 品質に満足しているか | なし→納品物の質を見直す |
| レビュー内容 | 買い手が何に価値を感じたか | 次の商品設計のヒント |

### 改善サイクル

```
出品 → 2週間観察 → 指標を確認 → 仮説を立てる → 修正 → 再観察
```

**注意**: 閲覧数ゼロの段階で説明文を直しても意味がない。まずタイトルとキーワードで検索に引っかかることが最優先。

## 受注時のオペレーション

### 受注から納品までの流れ
```
購入通知 → 内容確認（10分）→ 対応可否判断
  ├→ 対応可能 → Claude で下書き支援 → オーナーが構造化・編集（30-60分）→ 納品
  └→ 対応不可 → 丁寧にお断り＆返金
```

### Claudeの活用
1. 相談内容をClaudeに投げて初期分析を作成
2. オーナーが自分の経験・知見を加えて構造化
3. 回答をClaudeで推敲・校正
4. オーナーが最終確認して納品

**原則**: AIだけで完結しない。オーナーの経験に基づく判断・視点が必ず入ること。

### 受注量コントロール
- 初期は同時受注1件まで
- 慣れてきたら2-3件まで拡大
- ココナラの「受付休止」機能を活用

## AI-Human 役割分担

| タスク | AI | オーナー |
|--------|-----|---------|
| 市場調査（ココナラ検索・競合分析） | 調査・整理 | 確認・判断 |
| 出品文面の作成 | ドラフト作成 | 承認・修正 |
| ココナラ登録・出品 | - | 実施（本人確認必要） |
| 受注後の回答支援 | 初期分析・推敲 | 構造化・最終判断 |
| フィードバック分析 | データ整理・分析 | 意思決定 |
| 商品改善・新商品設計 | 提案 | 意思決定 |
